## D1. How was the certificate chain established for your private domain?

Because public Certificate Authorities (like Let's Encrypt) cannot verify private domains, we established our own local PKI (Public Key Infrastructure):
1. **Local CA:** We generated a private key and a self-signed Root CA certificate (`Team1 Local CA`).
2. **Server Certificate:** We generated a private key and CSR for `app.team1.test` (including SAN).
3. **Signing:** We used the Local CA to sign the server CSR, creating a valid certificate chain.
4. **Trust:** We imported the Local CA into the macOS System Keychain and marked it as "Always Trust".

## D3. What specific vulnerability does Subject Alternative Name (SAN) prevent that Common Name (CN) alone does not?

Relying solely on Common Name (CN) is deprecated and insecure because:
1. **Ambiguity:** CN was originally designed for identifying people or organizations, not just domain names.
2. **Single Domain Limitation:** CN typically only holds a single domain, making it difficult to secure multiple subdomains without wildcards.
3. **Security Standards:** Modern browsers (Chrome, Safari, Firefox) completely ignore the CN for hostname validation, relying strictly on the Subject Alternative Name (SAN) extension. Without SAN, modern clients will reject the certificate to prevent impersonation and Man-in-the-Middle (MITM) attacks.
